# Как кадрирует официальный инструмент Госдепа США

Разбор `tsg.phototool.state.gov` — эталона, на который ссылаются, когда говорят «а вот у них
кроп правильный». Всё ниже получено из их публичного клиентского кода и одного прогона
собственной фотографии через живой инструмент, 6 августа 2026.

## Что это вообще такое

Инструмент **целиком клиентский**, сервер не участвует. Стек виден в разметке:

| файл | роль |
|---|---|
| `tracking-min.js` + `eye-min.js` | детекция глаз, haar-каскады (tracking.js) |
| `objectdetect.frontalface_alt.js` | детекция лица, Виола-Джонс |
| `phototool-all-1.0.0.min.js` | их собственная геометрия |
| `exif-min.js`, `dpi-min.js` | ориентация и запись DPI |

То есть ведомство, задающее требования, решает ту же задачу теми же средствами, что и мы —
в браузере, без выгрузки снимка. Это, кстати, лучший аргумент в пользу нашей архитектуры,
какой можно было найти.

## Формула кадрирования

Из `calculateCropArea`, дословно:

```js
i = 0.41
u = (leftEye.x + rightEye.x) / 2         // центр между зрачками
g = (leftEye.y + rightEye.y) / 2
d = √((lx−rx)² + (ly−ry)²)                // межзрачковое расстояние

if (naturalWidth / d < 3.5) return null    // исходник слишком узкий

E = min(5.04, min(w/d, h/d)) · d           // сторона квадрата
crop.left = u − E/2
crop.top  = g − E · 0.41
```

Читается так: **сторона кадра равна 5,04 межзрачкового расстояния, а линия глаз стоит на
41 % высоты сверху.** Горизонтально кадр центрируется между зрачками, а не по лицу.

### Проверено на живом инструменте

Загрузил снимок 3024 × 4032. Их детектор нашёл глаза сам, инструмент выдал кадр
1555 × 1555 с верхом на 1102.

```
межзрачковое = 1555 / 5.04           = 309 px
центр глаз по вертикали              = 1739 px
от верха кадра: 1739 − 1102          = 637 px
637 / 1555                           = 41,0 %
```

Совпало с константой до десятой доли. Формула верна.

## Сравнение с нашими пресетами

Их же опубликованный допуск (Photo Composition Template): линия глаз на расстоянии
1⅛–1⅜ дюйма от низа снимка в 2 дюйма, то есть **56,25 % – 68,75 %**.

| | линия глаз снизу | с допуском ±3 п.п. | |
|---|---|---|---|
| их инструмент | 59,0 % | 56,0 – 62,0 | **выходит за нижнюю границу** |
| наш пресет | 62,5 % | 59,5 – 65,5 | внутри с запасом |

**Легенда не подтвердилась.** Их значение допустимо, но лежит близко к краю диапазона: любое
отклонение вниз — неточность детектора, наклон головы — выносит снимок за требование. Наши
62,5 % стоят посередине и дают запас в обе стороны.

Высота головы, наоборот, сходится. При кадре в 5,04 межзрачковых и обычном отношении
подбородок-макушка к межзрачковому 2,7–2,9 голова занимает 53,6–57,5 % кадра. Наш
`face_height_percent = 56` попадает ровно в середину.

## Побочные находки

- **`MAX_UPLOAD_SIZE_KB = 200`**, хотя официальное требование 240 КБ. Их инструмент подбирает
  качество JPEG в цикле, снижая по 0,03, пока не уложится в 200. То есть эталон строже
  собственной спецификации на 17 %.
- **`changeDpiDataUrl(u, 300)`** — 300 dpi прописывается в метаданные готового файла.
- **`naturalWidth / d ≥ 3.5`** — исходник отвергается, если лицо занимает слишком много кадра.
  Полезная проверка, которой у нас нет: снимок, сделанный вплотную, кадрировать уже нечем.
- **`MIN_EYE_DISTANCE = 20`** плюс требование, чтобы глаза стояли выше 59 % высоты исходника —
  так они отсеивают ложные срабатывания детектора.

## Что из этого стоит взять

1. **Проверку `ширина / межзрачковое ≥ 3.5`** — честный отказ лучше плохого кадра.
2. **Запись 300 dpi в метаданные** — у нас размер верный, а поле dpi в JPEG не проставляется.
3. Порог веса оставить свой: занижать до 200 КБ без причины значит терять качество там, где
  требование разрешает 240.

Линию глаз менять не надо. Мы ближе к центру допуска, чем эталон.
